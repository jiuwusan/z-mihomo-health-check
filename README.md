# z-mihomo-health-check

Go 后端与 Web 面板，通过 Mihomo API 探查当前出口，连续失败达到阈值后，按主分组原始顺序选择可用国家分组。

独立 Go 项目，一个容器可管理多个 Mihomo 实例，包含配置面板、470 个经三家美国出口验证的交集测试端点、后台自动探查、原始顺序切换、配置持久化及 Docker Compose 部署。部署步骤见 [DEPLOY.md](./DEPLOY.md)。

```sh
# wk 已存在时跳过创建
docker network create wk
docker compose config --quiet
docker compose pull
docker compose up -d
```

默认 [docker-compose.yml](./docker-compose.yml) 只启动健康检查服务，加入已有 `wk` 网络，连接现有 Mihomo。打开 [http://127.0.0.1:8080](http://127.0.0.1:8080)，填写后端可访问的 API 地址（例如 `http://mihomo:9090`）、Secret、目标分组，测试连接后启用并保存。首次安装默认停用。

Compose 参考 `z-media-workflow`：镜像 `jiuwusan/z-mihomo-health-check:latest`、同名容器、`restart: always`、45 秒停止宽限、持久化卷及 10MB × 3 日志轮转。镜像由 [GitHub Actions](./.github/workflows/docker-publish.yml) 自动构建并推送 Docker Hub，Compose 仅使用已发布镜像，部署机器只需部署文件，无需源码或 Dockerfile。

站点池见 [SITES.md](./SITES.md)，脚本可读取 [sites.txt](./sites.txt) 或 [sites.json](./sites.json)。探测记录见 [probe-results.json](./probe-results.json)。

## 1. 目标与使用场景

健康检查服务由 Go 后端和嵌入式 Web 面板组成，通过 API 连接已有 Mihomo。随本地迁移保留的订阅示例 `MY-1793463295556.yaml` 含真实凭据，已被 Git 和 Docker 构建上下文忽略；该示例包含 55 个 SS 节点、8 个国家/地区 fallback 分组，以及 `🚀 节点选择`、`🎯 全球直连` 两个 select 分组，仅用作策略组结构参考。

控制器管理 `🚀 节点选择`，保留国家分组及其内部的节点选择逻辑。国内直连规则维持订阅配置。后续运行配置不将主分组展开为 55 个实际节点。

页面加载、切换实例或保存连接配置后，会读取一次 Mihomo `/proxies` 节点信息，按主分组原始顺序展示国家分组及其当前实际节点；可点击“刷新”手动同步。此操作不调用 delay、不切换节点，也不改变探查失败计数。健康状态与延迟取自已有记录并标为“缓存”，没有有效历史时显示“-”；记录时间不是本次同步时间。普通面板轮询不会反复请求 Mihomo 节点信息；隐藏页面加载时等到页面可见再同步。节点同步失败会单独提示，保留已有展示，不影响后台自动探查。

## 2. 健康状态探查

已准备 [470 个三家美国出口共同通过的探查端点](./SITES.md)，覆盖大厂、知名开源项目、高校与机构。从 E-IX 美国基线、固定 Kuromis 美国 02 和固定 Sparkcloud 美国 02 的 488 个交集地址中，按最大实测延迟优先、同出口轮间波动及中位数延迟依次排序，保留前 470 个；每个地址在三家各通过三轮 4 秒限时探查、2 秒延迟门槛及逐地址历史状态审计。新加坡结果不参与筛选；不同时间的短窗口验证不代表长期可用率。

常规探查规则：

- 探查间隔默认 **5 秒**，可在面板配置为 1–86400 秒。
- 每轮从站点池中**均匀随机抽取 1 个站点**，测试 `🚀 节点选择` 当前选中的出口，不遍历整个池。
- 每轮重新随机选择，允许不同轮次抽中同一站点。
- 连续失败达到面板配置的阈值后触发主分组整组 delay 测试，随后按第 3 节规则选择可用国家分组；默认阈值为 **1 次**，成功一次即清零。

默认 5 秒间隔下，单个常规探查循环每分钟计划发起 12 次测试；470 个站点等概率抽取时，每个站点平均约 2350 秒（39 分 10 秒）被常规探查选中一次。修改间隔后，单站长期平均选中间隔为“站点数量 × 配置间隔”，不保证两次访问之间的最短间隔。失败触发的整组 delay 测试会增加实际出站请求；订阅原有的国家 fallback 分组也有独立探查，实际总量不受每分钟 12 次限制。随机分散请求用于降低单站访问频率，不能保证不触发风控。

常规探查调用 Mihomo 单代理 delay API，测试超时默认 4 秒，面板支持 1–32 秒。超时或测试失败累计出口失败次数；控制接口失联、认证或响应格式错误单独展示，不增加出口失败次数。后台串行调度，跨过的时钟周期跳过，不补发积压任务。本次交集池要求每个地址在三家美国出口各通过三轮 4 秒限时探查、2 秒延迟门槛及逐地址历史状态审计，不修改实例运行时配置。

“探查动态”支持勾选“仅查看失败”：显示当前实例最近一小时的警告和错误记录，隐藏成功及普通信息。筛选在分页前执行，支持查看更早的失败记录；关闭后恢复全部记录。开关状态保存在当前浏览器的 localStorage，刷新页面后自动恢复，并在首次加载记录时应用；浏览器存储不可用时仍可正常切换。筛选只影响展示，不改变探查或历史保存。

### 站点连续失败复核与临时隔离

所有实例共享站点的连续失败计数和临时隔离状态，保存在 `DATA_DIR/site-pool.json`，与“持久化历史记录”开关无关。任一实例的常规探查成功会清零该 URL 的计数；其他 URL 的结果不影响它。只累计常规出口探查失败，控制接口失联、认证错误、无效响应、任务取消、整组测试和优先级恢复检查均不额外累计。

前 19 次失败只计数，不增加复核请求。达到 **20 次**后，在本轮正常故障转移结束后复核：先测试两个不同的有效备用站点（仅剩一个时使用一个），全部成功后才重测原站点。原站点成功则清零；仍失败则全局临时隔离。备用站点也失败、没有备用站点、控制异常或复核前后当前选择变化时不隔离，同一 URL 至少冷却 **30 分钟**再复核，成功清零不会提前结束已有冷却。这样套餐到期造成的普遍出口故障不会直接触发全池剔除。

隔离项退出常规抽取和优先级恢复检查，**1 小时后**到期复测；所有实例合计每分钟最多复测一个隔离项，按最早到期优先。成功则全局恢复并清零，出口失败再等一小时，控制异常短暂退避。即使有效池为空，仍保留低频复测，不自动回填完整池。面板展示当前有效数量、总数量和隔离数量；事件记录复核、隔离与恢复。

计数、隔离和复测时间在重启后保留，保存失败时不发布未落盘的状态并记录错误；损坏的状态文件会阻止启动并提示检查。更新内嵌池时只载入仍在清单中的 URL，新地址默认可用。单出口交叉检查不能证明全球可用性，临时隔离和自动恢复用于限制误判影响。同一 `DATA_DIR` 仅供一个服务进程使用；该共享机制面向同进程管理的多个实例。

## 3. 节点自动切换策略

### 3.1 失败处理流程

1. 常规探查成功：保留当前选择；若开启自动恢复且到达恢复检查时间，再检查高优先级候选，随后等待下一个配置周期（默认 5 秒）。
2. 常规探查失败：累计失败次数。达到配置阈值后，若当前 A 组为受支持的 fallback、select 或 url-test，则先按下方类型规则探查 A 的直接成员，再从有效站点池随机抽取另一个 URL（排除本轮失败 URL 和隔离项）复验 A 出口。复验成功则保留 A、清零出口失败计数，本轮不执行主分组整组测试；原失败站点的独立计数不会因其他站点成功而清零，最近测试站点及日志显示实际复验 URL。复验仍失败、没有其他有效站点可选，或当前成员不适用该优化时，才执行 `🚀 节点选择` 的整组 delay。主分组整组测试仍使用本轮原始随机 URL，以便在相同目标下判定各国家分组的可用性。
3. 整组测试完成后，先确认主选择和成员顺序未在测试期间变化；若发生手动切换或订阅顺序变化，则停止本轮，不覆盖新选择。否则从有序列表的首项开始依次检查，选择本轮测试成功的第一个国家分组。**不按延迟数值排序，不使用 delay 响应 JSON 对象的遍历顺序。**
4. 若该分组就是当前选择，则保持当前选择；若不同，则通过 API 切换主分组。切换请求失败时，重新确认当前选择，尚未切换成功则按原顺序尝试下一个本轮通过测试的分组。
5. 全部分组不可用，或整组测试请求失败：保留当前选择，记录故障，下一周期重新执行常规探查，不进入无间隔重试循环。

每轮故障处理完成后恢复常规探查。控制器避免多轮故障处理同时运行；修改配置或停用会取消旧配置的任务、重置探查计数等当前状态，保留最近 1 小时的历史记录。

当前国家组自恢复只在达到失败阈值后执行，前几次失败不额外加测，只探查直接成员，不递归展开嵌套组。支持以下类型：

| 国家组类型 | 健康探查及组内选择 |
| --- | --- |
| `fallback` | 使用 A 的 `testUrl`、`expectedStatus` 执行整组 delay，由 Mihomo 自动选择；空 expected 原样传递 |
| `select` | 逐个探查直接成员；仅当前成员明确故障时，从原始 `all` 顺序选择首个可用成员。使用配置 URL；缺少 URL 时从有效池随机选非本轮失败 URL，expected 默认 `200-299` |
| `url-test` | 使用 A 的 URL/expected 逐个探查直接成员，由 Mihomo 自动选择，遵循其容差；不发送组内 PUT/DELETE，也不调用会解除固定的整组 delay |

`select`/`url-test` 的成员探查最多并发 8 个，并核对相应 URL 的健康记录，避免仅凭正延迟误判成功。`url-test` 当前仍指向故障成员且存在可用成员时，等待 10 秒选路缓存刷新再复验；配置变更可取消等待。自动组已有手动固定时跳过组内自恢复，继续主分组故障处理，不解除固定。

各类型复验均随机抽取有效池中其他 URL，排除本轮失败 URL 与隔离项；复验成功保留 A。fallback 整组测试全超时仍会复验 A；认证、连接或无效响应等控制错误停止本轮。探查及复验前后检查主选择、成员顺序，以及 A 的类型、成员、健康配置、固定状态；select 还检查组内选择，发现变化即停止旧流程。自动组允许 Mihomo 自行变更当前成员。API 不提供条件写入，最后检查与请求执行间的极短竞争无法原子排除。

A 组自恢复的健康探查固定 **5 秒**：fallback 整组 delay、select/url-test 每个直接成员 delay 的 `timeout` 均为 **5000 毫秒**，不受面板、环境变量或订阅超时配置影响，健康探查 HTTP 请求超时为 7 秒。常规出口探查、随机出口复验和主分组整组 delay 仍使用实例“探查超时”（默认 4 秒），各自的 HTTP 请求另留 2 秒。成员分批探查、状态读取、缓存等待和出口复验会使整个恢复流程超过单次测试超时；期间不补发常规探查。

可选的“自动恢复优先分组”默认关闭。开启后，启动探查或切换分组后先等待“首次最低间隔”（默认 300 秒），在当前出口探查成功的前提下开始首轮检查；后续每隔至少 60 秒，从站点池随机选一个 URL，依主分组原始 `all` 顺序逐个测试位于当前选择之前的成员，找到首个可用分组即停止；不执行整组 delay。相同候选连续 3 轮成功后，额外复验候选并重新读取当前选择和顺序，确认未变才回切。故障切换不受恢复等待限制。

首次最低间隔、恢复探查间隔和成功次数均可在面板调整。启动探查或换组后先等待首次最低间隔，再按恢复探查间隔连续验证；默认参数下三轮成功最早约在第 300、360、420 秒，随后立即复验回切，实际还受请求耗时和调度影响。候选失败/变化、API 错误、手动换组或顺序变化会重置连续计数；配置修改和重启也重新累计。进程启动及检测到手动换组时重新开始首次等待，普通保存不重新起算首次等待。恢复检查会增加出站请求，与常规探查串行执行，慢请求可能推迟后续探查，跳过错过的周期。面板显示首次检查剩余等待、恢复候选和成功次数，切换及候选变化进入近一小时记录。

国家分组列表展示最近一次整组或恢复探查结果和各项检测时间。恢复探查与回切前的额外复验都会更新实际被测分组的可用状态、延迟和 `checked_at`，未测试分组保留原结果与时间；尚未测试的分组显示“尚未探查”，测试失败显示“最近探查失败”。单次恢复成功即可显示可用，仍须连续成功达到阈值并通过复验后才回切。控制 API 认证、连接、格式异常或请求取消不覆盖已有节点结果；常规出口探查不改写这份列表。状态及检测时间保存在内存，修改配置或进程重启后重新探查，无需迁移存量配置。

### 3.2 国家分组优先级

当前示例中，`🚀 节点选择.proxies` 的原始顺序如下：

1. `🇺🇸 SS 美国`
2. `🇯🇵 SS 日本`
3. `🇸🇬 SS 新加坡`
4. `🇷🇺 SS 俄罗斯`
5. `🇬🇧 SS 英国`
6. `🇭🇰 SS 香港`
7. `🇹🇼 SS 台湾`
8. `🏳️ SS 其他`

例如，美国测试成功且延迟为 900 ms，日本测试成功且延迟为 100 ms，仍选择美国；只有美国本轮不可用，才检查日本，依此类推。每次故障恢复选择都从列表首项开始，不从当前分组的下一项开始。常规探查成功时不会为了回到高优先级国家而主动触发整组测试。

订阅更新后，以新配置的主分组原始顺序为准，不硬编码上述列表。运行时读取主分组的 `all` 数组，并在接入验证时核对它与生效配置的成员顺序一致。

### 3.3 Mihomo API

- `GET /proxies/{主分组名}`：读取当前选择 `now` 和有序成员列表 `all`。
- `GET /proxies/{主分组名}/delay?url={随机URL}&timeout={毫秒}&expected=200-299`：常规探查当前选择的出口。
- `GET /group/{主分组名}/delay?url={随机URL}&timeout={毫秒}&expected=200-299`：失败后测试主分组内的国家分组。
- `PUT /proxies/{主分组名}`，请求体 `{"name":"国家分组名"}`：选择国家分组。

默认主分组名为 `🚀 节点选择`，面板可加载并选择其他 select 分组；实际请求对路径分组名和查询 URL 分别编码。整组 delay 结果仅用于判定本轮可用性，不作为排序来源；不得用之前的历史成功记录代替本轮结果。结果缺项、0、负数或超出 uint16 范围视为本轮不可用。

接口依据：[Mihomo API 文档](https://wiki.metacubex.one/api/)。主分组按其直接成员原序选择；国家 select 组仅按上述故障恢复规则切换内部成员，不修改分组类型。

## 4. 配置与脚本

### 多实例管理

面板顶部选择当前实例，填写实例名称后可新增或重命名。每个实例独立保存 API 地址、secret、目标分组、探查/恢复参数与历史持久化开关，独立执行后台任务；切换面板不影响其他实例继续运行。新增实例默认关闭探查与历史持久化，不复制原实例的凭据。有未保存修改时，切换前提示确认。

桌面面板按视口高度排列运行指标、国家分组和探查动态，两个列表分别在面板内滚动，分组较多时不继续拉长页面。分组支持按名称搜索、查看可用数量和“定位当前”，搜索保留原始优先级编号。顶部“探查配置”和“管理实例”打开弹窗；配置按连接与探查、优先级恢复、历史与通知分区，保存按钮固定在弹窗底部，关闭或按 Esc 保留未保存草稿。手机端上下排列，列表仍各自限制高度并支持滚动。

页面正常显示时，在每轮状态刷新完成后等待 2 秒再请求。页面隐藏时暂停自动刷新并取消正在进行的自动刷新请求，重新可见时立即刷新；连续请求失败时，重试等待依次延长为 4、8、16、30 秒，之后保持最多 30 秒，成功后恢复 2 秒。切换实例会取消旧实例未完成的配置、状态、历史及连接测试请求，同时保留响应版本校验，避免旧响应覆盖当前页面；每次切换重新从正常间隔开始。页面轮询只读取状态，不触发节点探查，暂停页面刷新不影响后端持续运行。

首次启动创建一个未启用的“默认实例”，在面板重新填写连接信息。实例名称和顺序保存在 `/data/instances.json`；所有实例的配置和历史统一位于 `/data/instances/{实例ID}/`，不读取旧版根目录的配置或历史。所有文件共用现有数据卷，每个开启历史持久化的实例独立每 5 分钟保存近一小时记录，分页也只查询当前实例。

删除会停止该实例的探查并从列表移除，已保存的文件保留作备份，不再自动加载；至少保留一个实例，最后一个可通过关闭“启用自动探查”停用。停止容器时并行停止各实例，再分别补写已开启持久化的历史。

管理接口：`GET/POST /api/instances` 列表/新增，`PUT/DELETE /api/instances/{id}` 重命名/删除；新增和重命名提交 `{"name":"办公室"}`。实例业务接口为 `/api/instances/{id}/config`、`/status`、`/events`、`/groups`（均在相同实例前缀下）。所有业务请求必须显式携带实例 ID，不提供旧版无实例路径。

以下默认配置对每个实例独立生效：

| 配置项 | 默认值 |
| --- | --- |
| Mihomo API 地址 | `http://mihomo:9090`，按已有服务实际地址修改 |
| Secret | 面板输入，不回显；留空保留已保存值 |
| 目标分组 | `🚀 节点选择` |
| 探查间隔 | 5 秒 |
| 连续失败次数 | 1 次 |
| 探查超时 | 4 秒 |
| 启用自动探查 | 关闭 |
| 持久化历史记录 | 关闭，按需开启 |
| 自动恢复优先分组 | 关闭，需同时启用自动探查 |
| 首次最低间隔 | 300 秒，范围 0–86400 秒 |
| 恢复探查间隔 | 60 秒，范围 1–86400 秒 |
| 连续恢复成功次数 | 3 次，范围 1–100 次 |
| 钉钉群机器人 Webhook | 空，不发送钉钉通知 |
| 飞书群机器人 Webhook | 空，不发送飞书通知 |

每个实例可独立配置钉钉、飞书群机器人 Webhook，二者均为可选；同时配置则向两个群机器人发送格式化通知（钉钉 Markdown、飞书 Markdown 卡片）。面板保存后不回显链接，留空保留已保存值，勾选对应“清除 Webhook”并保存可停用该渠道。配置文件字段为 `dingtalk_webhook`、`feishu_webhook`；链接含机器人凭据，与 Secret 一样保存在实例配置文件中，请按凭据保管。已有配置无需迁移，默认不发送通知。

通知场景为：（1）节点故障后成功切换到可用节点；（2）自动恢复到高优先级节点；（3）达到失败阈值后整组测试确认所有节点均不可用。消息标题为 `Mihomo 节点状态变更`，包含实例名称、状态、分组、原节点、新节点和时间；状态分别为 `故障转移`、`节点恢复`、`全节点故障`，使用橙、绿、红图标区分，飞书卡片标题也采用对应颜色；这里的节点指主分组的直接成员（国家分组）。API 异常、候选验证尚未达标、保持当前选择或切换请求失败不发送上述通知。持续全部不可用只在首次确认时告警，探查恢复成功或整组测试发现可用成员后重新允许告警；该去重状态仅保存在内存，重启后重新判断。

通知在切换结果确定后发送，两个渠道并行，共用最多 3 秒的发送期限，可能使下一轮探查稍有推迟。发送失败仅记录历史警告，不回退切换、不改变节点健康状态，也不自动重试；可在探查动态中查看失败提示。不会记录链接、机器人响应正文或底层网络错误中的凭据。

三种场景共用以下 Markdown 正文，字段名加粗，空行分隔。钉钉使用原生 Markdown 消息，飞书使用带 Markdown 正文的卡片（标题在卡片头部展示）；两端使用同一套字段和状态含义。实例名称来自实例管理，重命名后后续通知使用新名称，不重置探查任务。名称、分组和节点中的 Markdown 特殊字符会转义。时间使用服务运行时区，默认容器配置为 `Asia/Shanghai`：

```markdown
### Mihomo 节点状态变更

**名称：** {实例名称}

**状态：** 🟠 故障转移 / 🟢 节点恢复 / 🔴 全节点故障

**分组：** {目标分组名称}

**原节点：** {切换前节点}

**新节点：** {当前节点}

**时间：** {yyyy-mm-dd hh:mm:ss}
```

每条消息仅显示实际发生的一种状态。全节点故障时保留当前选择，因此原节点与新节点相同。升级后请将机器人关键词同步改为 `Mihomo 节点状态变更`（原关键词 `Mihomo 状态变更` 不再包含在新标题中）。

机器人接入格式参考[钉钉自定义机器人](https://open.dingtalk.com/document/orgapp/custom-robot-access)和[飞书自定义机器人](https://open.feishu.cn/document/client-docs/bot-v3/add-custom-bot)。目前仅配置 Webhook 链接，未实现签名密钥；机器人如启用安全设置，请使用关键词 `Mihomo 节点状态变更` 或适当的出口 IP 白名单，开启加签的机器人需另行支持签名后才能使用。

Go 程序嵌入站点池和前端资源，无第三方 Go 依赖。配置默认存入 `./data/instances/{实例ID}/config.json`，容器中存入 `/data/instances/{实例ID}/config.json`。配置保存后立即生效；已启用的配置在进程重启后恢复运行。历史默认只存内存；面板开启“持久化历史记录”（`persist_history`）后，每 5 分钟批量保存到同目录 `history.json`，未变化时跳过写入，正常停止时额外保存一次。Secret 文件未静态加密，请按凭据文件保管。

首次安装的 API 地址使用 `wk` 网络中的服务名示例，已有配置文件中的地址原样保留；本机开发连接本机 Mihomo 时可填写 `http://127.0.0.1:9090`。Compose 在宿主机所有网卡发布面板端口，可通过服务器 IP 或域名访问，无需配置 Host 白名单；远程访问与数据卷说明见 [部署文档](./DEPLOY.md)。

## 7. GitHub Actions 发布镜像

工作流位于 [.github/workflows/docker-publish.yml](./.github/workflows/docker-publish.yml)，参考 `z-media-workflow`，沿用 Docker Hub Secret 命名和镜像标签约定。

1. 将本项目作为独立 GitHub 仓库的根目录上传，主分支使用 `master`。
2. 在 Docker Hub 准备 `jiuwusan/z-mihomo-health-check` 仓库，并创建具有该仓库推送权限的访问令牌。
3. 在 GitHub 仓库 **Settings → Secrets and variables → Actions** 配置 `OCKERHUB_USERNAME` 和 `DOCKERHUB_TOKEN`；用户名也兼容 `DOCKERHUB_USERNAME`，两者同时存在时优先使用 `OCKERHUB_USERNAME`。
4. 推送 `master`，或在 **Actions → Build and Push Docker Image → Run workflow** 手动触发。

流程先在 Ubuntu 上执行 Go 1.26 的 `go test -race`、`go vet` 和 Node.js 22 的 Web 检查，再通过 Buildx 构建并推送 `linux/amd64`、`linux/arm64` 镜像。`master` 发布 `latest`、`master`、`sha-<提交短哈希>`；手动构建其他分支发布分支和提交标签，不覆盖 `latest`。面向 `master` 的 PR 执行相同测试及双架构构建，但不登录 Docker Hub、不推送镜像。

运行应用不需要 Node.js，Node.js 仅供 CI 的 Web 回归测试。配置、历史文件、订阅和 API Secret 不进入镜像构建上下文，Actions 也不需要这些运行时凭据。官方参考：[Docker 多架构 GitHub Actions](https://docs.docker.com/build/ci/github-actions/multi-platform/)、[Go 环境设置](https://github.com/actions/setup-go)。

工作流成功发布镜像后更新服务：

```sh
docker compose pull
docker compose up -d
```

`latest` 镜像已通过 GitHub Actions 成功发布，支持 `linux/amd64`、`linux/arm64`。后续版本的构建与推送结果以 GitHub Actions 运行记录为准。Dockerfile 用于 CI 构建，部署 Compose 不包含 `build` 配置。
